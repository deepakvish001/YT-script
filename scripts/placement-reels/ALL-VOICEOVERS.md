## P01 · पहले कच्चा code, फिर पक्का

तुम्हारा roommate hard सवाल submit करके Maggi बनाने चला गया, और तुम चालीस मिनट से एक medium पर खाली editor घूर रहे हो। मम्मी सोचती हैं बेटा coding कर रहा है, पर बेटा cursor से staring contest खेल रहा है। तुम्हें लगता है roommate genius है, पर उसके पास एक process है, और तुम्हारे पास एक ज़िद है। उस ज़िद का नाम है perfectionism, यानी पहली line में ही perfect answer की चाह, और गलती का यही डर अक्सर शुरुआत ही नहीं करने देता। इसलिए तीन step याद रखो, कच्चा, पकड़ो, पक्का। पहला, कच्चा, यानी सबसे बदसूरत code जो सही answer दे, जैसे Two Sum में दो loop से हर pair check करना, जो n square है पर चलता तो है। दूसरा, पकड़ो bottleneck, यानी सबसे धीमा हिस्सा, और यहाँ वो अंदर वाला loop है जो हर number के लिए बाकी array छानता है। तीसरा, पक्का, यानी सिर्फ़ उसी का इलाज, देखे हुए numbers hash map में रखो, तो search लगभग एक झटके में होगी और code n square से n पर आएगा। मतलब loop में बार-बार search दिखे तो hash map, और sorted data में linear search दिखे तो binary search। Comment में BRUTE लिखो, मैं तुम्हें पूरी bottleneck table DM कर दूँगा, और follow कर लो।

## P03 · Constraints पढ़ो, algorithm पकड़ो
**Keyword:** `LIMIT`

एक ही सवाल पर एक बंदा story में खो जाता है, और दूसरा सीधा constraints देखकर पाँच सेकंड में algorithm का अंदाज़ा लगा लेता है। हम constraints को Terms and Conditions की तरह skip करते हैं, और फिर TLE पर judge को कोसते हैं। इसके पीछे satisficing है, यानी best की जगह पहले चलने वाले तरीके पर रुक जाना, इसलिए sample pass होते ही दिमाग बोलता है बस हो गया। इसका इलाज है एक second का बजट, क्योंकि rule of thumb है कि judge एक second में करीब 10 की power 8 simple operations चलाता है। अब n है 10 की power 5 और तुमने n square लिखा, तो हुए 10 की power 10, यानी बजट से सौ गुना ज़्यादा, सीधा TLE। वहाँ n log n या उससे तेज़ चाहिए, जैसे sorting, binary search या heap। n बीस तक है तो 2 की power n चलेगा, यानी backtracking या bitmask DP। पाँच सौ तक n cube, और पाँच हज़ार तक n square चलेगा। और n 10 की power 18 हो तो एक loop भी नहीं चलेगा, वहाँ log n चाहिए, जैसे binary exponentiation। ये reel save कर लो। Comment में LIMIT लिखो, मैं तुम्हें पूरी constraint table DM कर दूँगा, और follow कर लो।

## P05 · DSA में full marks, फिर भी reject?
**Keyword:** `CORE`

दोनों coding questions दस मिनट में green हो गए, मन में party शुरू हुई, और फिर interviewer ने पूछा कि deadlock कब होता है, तो दिमाग खुद deadlock में चला गया। Core subjects इसलिए छूटते हैं क्योंकि LeetCode की streak रोज़ हरी होती है, पर OS पढ़ने की कोई streak नहीं होती, तो वो progress जैसा लगता ही नहीं। Psychology में इसे focusing illusion कहते हैं, यानी जिस चीज़ पर ध्यान टिका हो, वो असल से ज़्यादा ज़रूरी लगती है। लेकिन कई companies coding के बाद technical round में OS, DBMS, Computer Networks और OOP पूछती हैं। जैसे deadlock के लिए चार conditions एक साथ चाहिए, mutual exclusion, hold and wait, no preemption और circular wait, और एक भी तोड़ दो तो deadlock नहीं होगा। ऐसे ही index से search fast इसलिए है, क्योंकि ज़्यादातर databases का B+ tree पूरी table scan की जगह कुछ steps में row तक पहुँचा देता है। तो मेरा Chai Core plan अपनाओ, यानी रोज़ DSA के बाद एक chai जितना time, करीब बीस मिनट, एक core topic को दो, और जवाब दोस्त को बोलकर समझाओ। Comment में CORE लिखो, मैं तुम्हें चारों subjects के must-know सवालों की cheat sheet DM कर दूँगा। Follow कर लो, ताकि अगली बार दिमाग deadlock में न जाए।

## P27 · पहले nets, फिर match: dry run
**Keyword:** `DRYRUN`

पचास line लिखीं, run किया, output अजीब आया, और तुमने Ctrl A, Delete दबाकर बीस मिनट की मेहनत उड़ा दी। दोबारा लिखा, वही गलती फिर आई, क्योंकि गलती code में नहीं, सोच में थी। हम सोचने की जगह type क्यों करते हैं? क्योंकि दिमाग को typing असली काम लगती है और सोचना टाइमपास, इसे action bias कहते हैं, यानी चुप बैठने से बेहतर कुछ भी कर देने की खुजली। Penalty पर goalkeeper ज़्यादातर किसी side dive मारता है, क्योंकि खड़े-खड़े goal खाना ज़्यादा बुरा लगता है, और हम वही dive keyboard पर मारते हैं। इसलिए rule है, पहले nets, फिर match। पहला, algorithm कागज़ पर चार पाँच steps में लिखो। दूसरा, छोटा input लेकर table में हर step के बाद variables की value भरो, यही dry run है। तीसरा, edge cases फेंको, खाली array, एक element, duplicates, negative numbers और सबसे बड़ा size। जैसे maximum ढूंढने में max को zero से शुरू किया, तो सारे numbers negative होने पर answer zero आएगा, जो array में है ही नहीं, ये bug table में दिख जाता है। कागज़ पर सब सही चले, तब type करो, क्योंकि अब coding बस translation है। Comment में DRYRUN लिखो, मैं तुम्हें template और edge case list DM कर दूँगा, और follow कर लो।

## P28 · Logic सही, फिर भी TLE?
**Keyword:** `TLE`

Sample पास, logic सही, फिर भी submit पर TLE आ गया, यानी time limit पार। Answer सही था, बस वो उस दोस्त जैसा निकला जो पाँच मिनट बोलकर घंटे भर बाद आता है। तीन वजहें होती हैं। पहली वजह गलत data structure है, जैसे loop में list पर contains हर बार पूरी list घूमता है, जबकि hash set में ये average O(1) है। n एक लाख हो तो करीब 10 की power 10 operations बनते हैं, यानी 1 second की limit में करीब सौ गुना देर। और बार बार minimum चाहिए, तो list नहीं, priority queue लो। ये आदत की गलती है, इसे Einstellung effect कहते हैं, यानी पुराना तरीका इतना पक्का कि बेहतर रास्ता दिखता ही नहीं। दूसरी वजह है अनजाने में बनी copy। C++ में recursion में vector by value भेजा तो हर call पर copy बनती है, const reference से भेजो। Java में array भेजने पर copy नहीं बनती, पर loop में String को plus से जोड़ना हर बार नई string बनाता है, StringBuilder लो। Python में slicing भी नई list बनाती है। तीसरी वजह है धीमा algorithm, तब constraints देखो और approach बदलो। Comment में TLE लिखो, मैं तुम्हें TLE checklist DM कर दूँगा, और ऐसे ही placement के सच के लिए follow कर लो।

## P29 · पिछले हफ़्ते Accepted, आज blank: "देखा हुआ है" syndrome
**Keyword:** `REVISE`

पिछले हफ़्ते जिस सवाल का Accepted screenshot तुमने status पर लगाया था, आज वही खोला तो दिमाग़ बोला, ये कौन है भाई? इसे मैं कहता हूँ "देखा हुआ है" syndrome, यानी सवाल पहचान में आता है, पर लिखा नहीं जाता। ये कमज़ोरी नहीं, forgetting curve है, जो Ebbinghaus ने 1885 में दिखाया था, यानी नई सीखी चीज़ शुरू में सबसे तेज़ी से भूलती है, अगर दोबारा याद न करो। ऊपर से हम revision के नाम पर पुराना code बस पढ़ लेते हैं, जिससे लगता है याद है, पर दिमाग़ ने खुद कुछ निकाला ही नहीं। तो revision ऐसे करो। Blank file खोलो, बिना देखे solve करो, और target रखो कि पहले run में ही सही चले। Test case fail हो तो solution tab मत खोलो, उसी failing case पर code line by line dry run करो, और जहाँ value गलत हुई वहीं logic ठीक करो। और हाँ, if n बराबर 5 तो return 3 लिखना fix नहीं, जुगाड़ है। ये re-solve बढ़ते gap पर करो, जैसे दिन 1, 3, 7 और 21 पर। इसके पीछे spacing effect है, यानी gap देकर किया revision एक साथ रटने से ज़्यादा टिकता है। Comment में REVISE लिखो, मैं तुम्हें revision tracker template DM कर दूँगा, और follow कर लो।
